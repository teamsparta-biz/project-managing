# 콘테스트(해커톤) 심사 스킬

`/contest-judging [콘테스트 URL] [평가결과 템플릿 xlsx 경로]` 실행 시, contest-platform에 제출된 모든 산출물을 실제로 다운로드해 코드·스크린샷을 확인한 뒤 점수와 심사평을 작성하고, 지정된 엑셀 템플릿 양식에 맞춰 채워 넣습니다.

> 트리거: "콘테스트 심사해줘", "해커톤 결과물 채점해줘", "이 제출물들 평가해줘", "평가결과 템플릿 채워줘" 같은 표현. 인자가 부족하면(URL 또는 템플릿 경로 없음) 사용자에게 물어본다.

## 핵심 원칙

1. **추측 금지**: 모든 점수·심사평은 반드시 실제 제출 파일(HTML 소스코드)과 스크린샷을 열람한 후 작성한다. 설명(description)만 보고 점수를 매기지 않는다.
2. **제출자명은 항상 실명 "이름(부서명)" 형식**. 콘테스트 플랫폼의 `/api/submissions`가 주는 `user.name`은 이메일 아이디(예: `yunsang.ji`)일 뿐 실명이 아니므로 절대 그대로 쓰지 않는다. 반드시 `/api/gallery`의 `user.display_name`에서 실명+부서를 가져와 정규화한다 (아래 3단계).
3. **바로 송부 금지**: 결과를 정리해 사용자에게 먼저 보여주고 검토·확인을 받은 뒤에만 최종 파일을 저장한다. Slack/메일 등으로 즉시 전달하지 않는다.
4. **템플릿 원본은 읽기 전용**: 지정된 템플릿 xlsx를 직접 덮어쓰지 않는다. 템플릿을 불러와 값을 채운 뒤 새 파일로 저장한다.

## 실행 흐름

### 1단계: URL 파싱

전달받은 콘테스트 URL(랜딩 페이지 `/{tenantSlug}/{contestSlug}` 또는 갤러리 `/{tenantSlug}/{contestSlug}/gallery` 형태 모두 가능)에서 `tenantSlug`, `contestSlug`를 추출한다.

### 2단계: 제출물 목록 조회

```
GET https://contest-platform-production.up.railway.app/api/gallery?slug={tenantSlug}&contestSlug={contestSlug}
```

응답 JSON의 `submissions` 배열을 사용한다 (`curl -s "..." -o /tmp/gallery.json` 후 Python으로 파싱 — `/api/submissions?contest_id=...` 대신 이 엔드포인트를 쓰는 이유는 `user.display_name`에 실명+부서가 들어있기 때문). 각 항목에서 다음을 확보한다:
- `title`, `description`
- `file_url` (HTML 등 제출 파일), `external_link` (파일 대신 외부 링크만 제출한 경우)
- `screenshot_url`
- `user.display_name` (실명+부서, 표기가 제각각일 수 있음)

### 3단계: 제출자명 정규화 — `이름(부서명)`

각 제출물의 `user.display_name`을 다음 규칙으로 `이름(부서명)` 형태로 통일한다 (이미 검증된 규칙, `contest-gallery-html-zip` 스킬과 동일):

1. 이미 `이름(부서명)` 형태(끝이 괄호로 닫힘)면 이름/부서명 사이 공백만 정리.
2. `이름/부서명`처럼 슬래시 구분이면 슬래시를 기준으로 분리해 `이름(부서명)`으로 변환.
3. `이름 부서명`처럼 공백 구분(괄호 없음)이면 첫 공백을 기준으로 분리해 `이름(부서명)`으로 변환.
4. 위 규칙으로도 분리가 안 되면(부서 정보 없음) display_name을 그대로 사용.
5. 부서명 안에 `/`가 있으면 파일/셀에 쓰기 전에 `_`로 치환할 필요는 없지만(엑셀 셀이므로 그대로 둬도 무방), 표기가 어색하면 다듬는다.

`display_name`이 비어있거나 없는 제출물은 `user.name`(이메일 아이디)으로 대체하되, 반드시 사용자에게 "실명 확인 불가" 항목으로 별도 보고한다.

### 4단계: 템플릿 양식 파악

지정된 평가결과 템플릿 xlsx를 openpyxl로 열어 시트명·헤더 컬럼 순서를 확인한다. 표준 템플릿은 `제출자 | 제목 | 실용성 | AI활용도 | 완성도 | 확장성 | 총점 | 심사평` (각 세부항목 0~25점, 총점 0~100점) 구조이지만, 실제 헤더를 읽어 그대로 따른다.

같은 폴더(또는 Drive 내)에 과거 채점이 완료된 유사 템플릿 파일(예: `*_평가결과.xlsx`, 헤더 행 아래 실제 점수·심사평이 채워진 파일)이 있으면 함께 열어 **심사평의 톤·깊이·분량을 캘리브레이션하는 참고 예시**로 쓴다. 못 찾으면 아래 기본 스타일 가이드를 사용한다.

### 5단계: 산출물별 채점 (병렬 서브에이전트)

제출물 수가 많으면(대략 5개 초과) Agent 도구로 5개씩 묶어 병렬로 서브에이전트를 실행한다. 각 서브에이전트 프롬프트에 반드시 포함할 것:

- 담당할 인덱스 범위와, 그 인덱스에 해당하는 **정확한 제목·제출자**를 명시해 서브에이전트가 배열을 스스로 슬라이싱하다 인덱스를 착각하지 않도록 한다 (과거 실행에서 인덱스 오프셋 실수로 동일 항목이 중복 평가되고 다른 구간이 누락된 사고가 있었음 — 반드시 담당자에게 "이 인덱스는 반드시 이 제목과 일치해야 한다"는 확인 문구를 줄 것).
- `file_url`을 curl로 다운로드해 실제 HTML/코드를 읽고 기능·로직·완성도를 확인 (external_link뿐이면 WebFetch).
- `screenshot_url`을 curl로 다운로드해 Read 도구로 이미지를 직접 열람, 설명과 실제 화면이 일치하는지 확인.
- 아래 평가 기준과 심사평 스타일 가이드를 그대로 전달.
- 출력은 `{index, title, submitter, 실용성, AI활용도, 완성도, 확장성, 총점, 심사평}` 형태의 JSON 배열만.

**평가 기준 (각 세부항목 0~25점, 총점 0~100점 — 템플릿이 다른 배점이면 그에 맞게 조정):**
- 실용성: 실제 업무에 바로 쓸 수 있는 정도, 문제의식의 명확성
- AI활용도: AI를 활용해 구현한 로직/아키텍처의 정교함, 단순 템플릿이 아닌 실제 동작하는 로직 여부
- 완성도: 코드가 실제로 동작하는지, 스크린샷이 설명과 일치하는지, 빈 화면/미완성 여부, 설명과 실제 구현 사이 괴리 여부
- 확장성: 다른 부서/업무로 응용 가능한 범용성 vs 특정 부서·업무에 종속적인 정도

**심사평 스타일**: 3~5문장, 평서체(~다/~있다/~보인다). 구체적인 구현 디테일(함수명·로직·UI 요소)을 근거로 들고, 스크린샷 확인 여부를 반드시 언급하며, 장점뿐 아니라 구체적인 약점·한계도 짚는다. 막연한 칭찬/비판 금지 — 항상 코드나 화면에서 본 구체적 사실에 근거한다.

### 6단계: 결과 취합 및 검증

모든 서브에이전트 결과를 모아 스크래치패드에 JSON으로 저장한 뒤 다음을 검증한다:
- 인덱스가 0부터 (제출물 수-1)까지 빠짐없이, 중복 없이 존재하는지
- 각 항목의 세부점수 합 = 총점인지
- 제출자명이 모두 3단계에서 정규화한 실명(부서명)으로 채워졌는지 (이메일 아이디가 하나라도 남아있으면 안 됨)

문제가 있으면 해당 구간만 다시 서브에이전트를 실행해 보정한다.

### 7단계: 템플릿에 반영 및 요약 보고

- openpyxl로 템플릿을 열어 인덱스 순서대로 행을 채운 뒤(제출자=실명(부서명), 제목, 4개 세부점수, 총점, 심사평), **새 파일로** `~/Downloads/{tenantSlug}_{contestSlug}_평가결과/` 폴더에 저장한다 (다른 저장 위치를 사용자가 지정하면 그에 따른다).
- 점수 상위/하위 몇 건을 요약 표로 사용자에게 보여주고, 저장 경로를 안내한다.
- 이 시점에서 파일 송부(메일/Slack 등)는 하지 않는다 — 사용자가 검토 후 별도로 요청할 때만 진행한다.

## 자주 하는 실수

| 실수 | 방지 |
|------|------|
| `/api/submissions`의 `user.name`(이메일 아이디)을 제출자명으로 그대로 씀 | 반드시 `/api/gallery`의 `display_name`을 실명(부서명)으로 정규화해서 사용 |
| 서브에이전트가 배열 인덱스를 잘못 읽어 다른 구간을 중복 평가 | 각 서브에이전트 프롬프트에 담당 인덱스와 정확한 제목을 명시하고, 취합 단계에서 인덱스 중복/누락을 반드시 검증 |
| 스크린샷을 보지 않고 description만으로 채점 | 모든 항목에서 screenshot_url을 실제로 Read로 열람 |
| 템플릿 원본을 직접 덮어씀 | 항상 새 파일로 저장 |
| 채점 직후 바로 메일/Slack 발송 | 사용자 검토·확인 전까지 저장만 하고 송부하지 않음 |
